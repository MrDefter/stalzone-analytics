# Работа над STALZONE Analytics

## Структура

- Размещай интеграцию EXBO, планирование, сбор и публикацию аукциона в
  `auction_engine/backend/`. Здесь же находятся финансовые расчёты
  в `analytics/` и репозитории записи истории и снимков.
- Размещай FastAPI, маршруты, модели HTTP и подготовку графиков в
  `stalzone_analytics/backend/`. Точка входа Uvicorn доступна через
  `stalzone_analytics.app:app`. Шаблоны, статику и иконки храни в
  `stalzone_analytics/frontend/`.
- Используй `common/` для форматов хранения и команд, каталога,
  соединения с ClickHouse и переиспользуемого чтения данных.
  Общий пакет не импортирует сервисы. Веб-сервис читает опубликованные
  версии и передаёт команды ядру через ClickHouse.
- Размещай модели Pydantic, dataclass, перечисления и исключения у
  владельца соответствующей ответственности. Общие сущности храни
  в `common/models/`, `common/dataclasses/`, `common/enums/`
  и `common/errors/`.
- Объявляй настройки через `BaseSettings` из `pydantic-settings`.
  Используй переменные окружения и корневой `.env`, храни секреты в
  `SecretStr`. Общие настройки находятся в `common/settings/`,
  настройки EXBO и пределы ядра — в `auction_engine/backend/`.
  Каталог хранится в `common/settings/items/items.json`.
- Разбирай параметры запуска в `main.py` через `argparse`. Без имени
  предмета запускай веб-сервис и ядро, с именем — просмотр сохранённого
  снимка. Форматирование CLI находится в `stalzone_analytics/backend/cli/`.

## Python

- Используй Python 3.11+ и PEP 8. Отступы составляют 4 пробела, строки кода
  занимают до 79 символов, строки комментариев и docstring — до 72.
  Группируй импорты стандартной библиотеки, внешних зависимостей и проекта.
  Аннотируй публичные параметры и результаты.
- Пиши docstring на русском для всех модулей, классов, функций и методов,
  включая приватный код, вложенные обработчики и тесты. Начинай с краткого
  описания назначения. Описывай параметры в `Args`, кроме `self` и `cls`,
  а возвращаемые значения — в `Returns`. Добавляй разделы по сигнатуре.
- Декомпозируй по ответственности. Держи модели, ввод-вывод, авторизацию и
  бизнес-логику в отдельных модулях. Объединяй в классе состояние и операции
  над ним. Выноси в функции преобразования, которым состояние не нужно.
- Переиспользуй существующую логику и сохраняй публичные импорты и поведение
  при рефакторинге. Передавай в логи и сообщения об ошибках только безопасные
  метаданные запросов. Храни реальные учётные данные в локальном `.env`.

## Проверки

- Устанавливай dev-зависимости из `requirements-dev.txt`. **Запускай тесты
  только по прямому запросу пользователя.** Команда для запуска из корня
  проекта — `python -m pytest -q`. Для автономных тестов API используй
  `httpx.MockTransport`.
- **Запускай Ruff только по прямому запросу пользователя.** Это относится
  к проверке, форматированию и исправлениям. Настройки Ruff лежат в
  `ruff.toml`.

## Экономия контекста и лимитов Codex

### 1. Точечное изучение проекта

- Не перечитывай весь репозиторий перед каждой задачей.
- Начинай с файлов, прямо указанных в запросе, и их непосредственных
  зависимостей.
- Для поиска используй точечные команды (`rg`, выборочное чтение файлов).
- Не выводи целые большие файлы, если достаточно посмотреть отдельную
  функцию или участок.
- Не повторяй чтение уже изученного кода без необходимости.

### 2. Минимальный объём изменений

- Изменяй только то, что необходимо для выполнения задачи.
- Не проводи попутный рефакторинг, переименование, форматирование или
  изменение архитектуры без необходимости.
- Не создавай новые абстракции и модули, если достаточно исправить
  существующую функцию.
- Не изменяй несвязанные файлы.
- При выборе между равнозначными решениями предпочитай более простое,
  соответствующее текущей архитектуре.

### 3. Экономия на планировании

- Для небольших однозначных задач переходи непосредственно к реализации.
- Для сложных задач составляй краткий внутренний план, без длинных
  рассуждений в ответах.
- Не повторяй полное описание задачи и уже известный контекст.
- Не проводи альтернативные архитектурные исследования, если решение и
  границы изменений уже определены пользователем.
- Не задавай вопросы, ответы на которые можно получить из текущего кода
  и задания.

### 4. Инструменты и агенты

- Не запускай дополнительных агентов для простых локальных изменений.
- Не выполняй параллельные исследования одного и того же участка кода.
- Используй дополнительные инструменты и агентов только тогда, когда они
  дают практическую пользу для решения задачи.
- Не запускай команды, не относящиеся к заданию.
- Ограничивай объём выводимых логов, результатов поиска и диагностической
  информации.

### 5. Проверки

- Запускай pytest и Ruff только по прямому запросу пользователя.
- Не выполняй дополнительные масштабные проверки без необходимости.
- При необходимости проверяй изменение максимально локально.
- Не обращайся к production API без явной необходимости и разрешения.
- Не выдавай непроверенный результат за проверенный.

### 6. Отчёт о выполнении

В кратком отчёте указывай, какие файлы изменены, что исправлено или
реализовано, какие проверки выполнены и какие ограничения или нерешённые
проблемы остались. Не пересказывай весь процесс работы и не дублируй
техническое задание.

### 7. Приоритет корректности

Экономия токенов не должна приводить к неполной реализации требований,
пропуску важных зависимостей, нарушению существующих контрактов, сокрытию
ошибок или ухудшению безопасности и качества кода.

Для сложных задач изучай дополнительные файлы, выполняй необходимую
диагностику и подробно анализируй проблему.

Применяй эти правила по умолчанию ко всем будущим задачам проекта.
Прямые инструкции пользователя имеют приоритет.
