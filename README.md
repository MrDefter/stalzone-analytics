# STALZONE Analytics

## Установка

Нужен Python 3.11 или новее. Запускайте команды из корня проекта в активированном виртуальном окружении.

```shell
python -m pip install -r requirements.txt
```

## Веб-интерфейс

После установки зависимостей и запуска [ClickHouse](#clickhouse)
запустите из корня проекта

```shell
python main.py
```

По умолчанию сервис доступен по адресу [127.0.0.1:8000](http://127.0.0.1:8000).
Адрес и порт можно задать через `--host` и `--port`.

```shell
python main.py --host 127.0.0.1 --port 8080
```

Интерфейс получает настроенные предметы через `GET /api/items`. Маршрут
читает `common/settings/items/items.json` при каждом запросе и возвращает
названия, ID, параметры партии и локальные ссылки на иконки. Обновите
страницу после изменения каталога.

При выборе предмета `GET /api/auction/analysis` читает опубликованные
лоты, готовую оценку и продажи из ClickHouse. Запрос принимает
`item_id` из каталога, `region=RU`, `mode=production`, период
графика `days` и параметры стратегии `min_sales` и `min_roi_bps`.
Индикатор **Live RU · EXBO** показывает источник данных. Укажите
`STALZONE_CLIENT_ID` и `STALZONE_CLIENT_SECRET` в
окружении процесса или в корневом `.env`. Данные доступа используются
на сервере. [Справка EXBO](https://eapi.stalzone.com/reference)

По умолчанию Production трактует цены выкупа и завершённых сделок
как полную стоимость лота. Комиссия составляет 5% и округляется вверх
до целого игрового рубля. Невозвратные расходы на выставление равны
нулю, а временный залог исключён из ROI.

`STALZONE_PRODUCTION_ANALYSIS_RULES` позволяет задать серверное
переопределение. Ключ `listing_cost_per_pack` указывает расход на
выставление стандартной партии. Правила Demo задаются отдельно.
Однородность предмета и размер стандартной партии берутся из каталога.

В окне «Настройки модели» можно изменить минимум сопоставимых продаж
(`min_sales` от 5 до 200, по умолчанию 20) и минимальный ROI
(`min_roi_bps` от 0 до 10 000 с шагом 10, по умолчанию 1000). В форме
ROI задаётся в процентах с шагом 0,1%. «Применить» сохраняет стратегию
для всех предметов в браузере и запускает один новый расчёт.

Модель выбирает кратчайшее полностью покрытое окно из 3 часов,
24 часов, 7 и 14 дней, в котором набран заданный минимум продаж.
Если такого окна нет, для предварительного Q25 берётся кратчайшее
окно с достаточным числом полученных продаж.
Q25 рассчитывается методом ближайшего ранга по полным ценам продаж
партий размера `sell_quantity`. Для сравнения Q25 с предыдущим окном
той же длины требуются подтверждённое покрытие и достаточное число
продаж в обоих окнах. Падение на 20% и более блокирует рекомендацию
к покупке.

Наблюдаемый суточный оборот и активное предложение измеряются в
стандартных партиях. Для проверки ликвидности модель резервирует
`ceil(amount / sell_quantity)` партий на покупку и исключает
оцениваемый лот из его конкурентов. Если конкуренты превышают остаток
оборота, цена выхода может быть снижена до цены граничного предложения
минус один игровой рубль.

Комиссия и выставление рассчитываются на стандартную партию. Затем
модель умножает её чистую выручку на точную долю
`amount / sell_quantity`, округляет результат вниз и вычитает полную
цену выкупа. Для некратного количества это оценка при последующей
комплектации стандартных партий.
При предварительном Q25, неполном снимке или устаревшей истории кандидаты
помечаются «Оценочно выгодно». Окна Q25, суточного оборота и графиков
отсчитываются от указанной в ответе границы `history.covered_until`.
Активность лотов проверяется на момент запроса.

График истории цен доступен без финансовых правил. В каждом интервале
он показывает медиану полной цены продаж партий указанного размера.

Графики по умолчанию показывают последние 24 часа. При смене периода
сервер берёт нужный участок из ClickHouse. Интерфейс показывает время
последней успешной синхронизации, подтверждённый диапазон и ошибки.

Сборщик EXBO запрашивает по 200 строк на страницу. Лоты ограничены пятью
страницами. После первого запроса сборщик читает до восьми страниц истории
или двух страниц лотов параллельно. Проверки перекрытий и повторная сверка
опорной страницы защищают от сдвига списка. При недоступном ClickHouse
API сообщает об ошибке хранилища. При сбое обновления EXBO интерфейс
показывает последнюю опубликованную версию и её возраст.

На графике цены одиночные наблюдения отмечены точками, а интервалы без
цены образуют разрывы. Подсказки указывают, покрыт ли интервал полностью.
На графике ликвидности нули видны только для подтверждённых интервалов.

Записи журнала ядра связаны по `snapshot_id`. Строка `EXBO page`
показывает ресурс, этап, смещение, размер страницы, длительность и статус
HTTP, если получены заголовки. При сбое видны тип ошибки и безопасное
описание, а для HTTP 429 выводится разобранный `Retry-After` в секундах.
Штатный повтор после HTTP 401 отмечается отдельной записью `status=retry`.

Строка `EXBO scan` показывает число начатых и успешно прочитанных страниц
и число разобранных строк с учётом перекрытий и контрольной сверки.
Счётчики страниц учитывают загрузки сборщика, а попытки HTTP видны в
строках `EXBO page`. При сбое или отмене без `PageScan` полнота и
согласованность имеют значение `None`. Если проверка дала отрицательный
результат, в завершённом снимке эти признаки имеют значение `False`.

Денежные суммы передаются десятичными строками в целых игровых рублях.
`q25_per_pack`, `exit_price_per_pack` и `net_revenue_per_pack`
относятся к одной стандартной партии. Суммы `*_total` относятся ко
всей покупке. Интерфейс рассчитывает цены за предмет для отображения
из соответствующих сумм и количества. `turnover_24h`,
`active_competing_packs` и `sample_count` измеряются в партиях.
ROI передаётся числом в процентах, неизвестные показатели — `null`.
Номер лота в таблице относится к текущему снимку.

Иконки лежат в `stalzone_analytics/frontend/item_images/` под именами
`<item_id>.png`. Чтобы скачать недостающие файлы по индексу EXBO, запустите
из корня проекта

```shell
python -m scripts.sync_item_icons
```

Флаг `--force` обновляет уже сохранённые файлы. При отсутствии PNG
интерфейс показывает нейтральную иконку. Синхронизация использует публичный
репозиторий. [Индекс EXBO для RU](https://raw.githubusercontent.com/EXBO-Studio/stalzone-database/main/ru/listing.json)

## ClickHouse

Добавьте параметры ClickHouse из `.env.example` в корневой `.env` и
задайте `STALZONE_CLICKHOUSE_PASSWORD`. Переменные окружения имеют
приоритет. Порт по умолчанию `8123` опубликован только на `127.0.0.1`.
Если он занят, задайте свободный порт через `STALZONE_CLICKHOUSE_PORT`.

```shell
docker compose up -d --wait
python main.py
```

`main.py` запускает Uvicorn с одним worker и отдельный процесс
`auction_engine`. При сбое ядра запускающий процесс повторяет попытку
с задержкой до 30 секунд. При штатной остановке завершаются оба процесса.
Для независимого запуска используйте два терминала.

```shell
python -m auction_engine
uvicorn stalzone_analytics.app:app --workers 1
```

Поддерживается один писатель на локальный экземпляр ClickHouse. Прямой
запуск Uvicorn обслуживает сохранённые данные независимо от ядра.

Один сервер ClickHouse хранит две базы. В `stalzone_history` находятся
таблицы `auction_history_ru_<item_id>`, таблицы порций с суффиксом
`_batches`, журнал `history_batch_commits` и `history_sync_state`.
История хранится до 30 дней, ранее сохранённые продажи остаются доступны. В `stalzone_snapshots` находятся
`auction_snapshots`, `snapshot_lots`, `snapshot_analysis`,
`scanner_state`, `scanner_settings` и `scanner_commands`. Схема
создаётся автоматически. Данные сохраняются в томе `clickhouse_data`.
Предыдущая база `stalzone` остаётся на диске.

Перед первой публикацией снимка сборщик загружает подтверждённую историю
за последние 24 часа или до конца доступного списка EXBO. Пока идёт
загрузка или ожидается повтор после сбоя, интерфейс показывает её статус.
После этого сборщик догружает более ранние сделки небольшими порциями до
границы хранения или конца доступной истории EXBO. Обычное обновление
читает свежие сделки до сохранённой границы с контрольным перекрытием.
Конец доступного списка завершает догрузку. Если список заканчивается
раньше запрошенной границы, покрытие остаётся в пределах подтверждённых
данных. Если обновление возвращает пустой список после накопления
истории, сборщик сохраняет прежние границы и повторяет попытку позже.
Планировщик проверяет задачи каждые 5 секунд. По умолчанию история
обновляется каждые 60 секунд, а лоты каждого из четырёх отслеживаемых
предметов — каждые 180 секунд. Одновременно работают до двух предметов.
Общий предел составляет 8 одновременных HTTP-запросов и 60 стартов
запросов за минуту. Интервалы и лимиты задаются в `.env.example`.
История использует 120 секунд контрольного перекрытия.

После проверки страниц сохраняются только полностью прочитанные группы
с одинаковым временем. Сигнатура включает время, количество, цену и
канонический JSON `additional`. Номер вхождения сохраняет кратность.
Повторный проход дописывает недостающие вхождения. Новая порция продаж
становится видимой после записи маркера и контрольной точки. График и
расчёт используют одну ревизию истории, даже если она обновилась во время
запроса. Если EXBO изменит поля
ранее опубликованной сделки, без `sale_id` её нельзя надёжно сопоставить.
Позднее появление сделки за пределами контрольного перекрытия может
остаться незамеченным. Сдвиг страниц или неразличимые целиком совпавшие
страницы оставляют контрольную точку на последней проверенной границе.

Журнал `History sync` показывает вид операции, число запросов страниц,
полученные и добавленные записи, дубли, границы покрытия и тип ошибки.
После записи лотов и оценки ядро добавляет маркер публикации. Снимки и
стандартные расчёты хранятся три дня. Временные профили хранятся до
30 минут, максимум 32 на снимок. Параметры Q25 и ROI образуют профиль
расчёта по уже сохранённым данным. Пока профиль готовится, API отвечает
HTTP 202. Фронтенд раз в 5 секунд запрашивает версию результата и
загружает полный ответ при её смене. При открытии устаревшего снимка
веб-сервис ставит одно фоновое обновление для текущей версии, в том числе
при выключенном мониторинге. Доступный снимок остаётся видимым.

`GET /api/engine/status` возвращает состояние планировщика.
`GET /api/auction/version` возвращает версию расчёта и его актуальность.
`GET /api/auction/history/status` показывает покрытие истории.
`POST /api/auction/refresh` ставит обновление в очередь.
`PATCH /api/auction/monitoring` принимает поля `monitoring`, `interval`
и `priority`. Эти маршруты принимают `item_id`, `region` и `mode`
как параметры запроса. Результат команды доступен через
`GET /api/auction/commands/{request_id}` с тем же ключом предмета.

Локальная проверка публикации истории выполняется командой
`python -m scripts.smoke_history_revision`. Она использует временную базу
в настроенном ClickHouse и обходится без EXBO.

## Список предметов RU

Команда читает `common/settings/items/items.json` через
`ItemCatalogSettings`. Добавляйте предметы в массив `items` как объекты
с точным `item_id` и русским `name_ru`. Поиск проверяет точный ID,
полное имя и часть имени в этом порядке. Первые записи сверены с
[каталогом EXBO](https://github.com/EXBO-Studio/stalzone-database/tree/main/ru/items/other).

## Просмотр аукциона

Запустите из корня проекта в активированном окружении. Команда читает
опубликованный снимок выбранного предмета и режима из ClickHouse.

```shell
python main.py "Стандартные запчасти" --mode production
python main.py y3nmw --mode production --limit 20 --json > sales.json
python main.py --help
```

Для заполнения production ядру нужны `STALZONE_CLIENT_ID` и
`STALZONE_CLIENT_SECRET`, а для demo — `STALZONE_DEMO_TOKEN`.
Укажите их в `.env` или в окружении процесса ядра. Для просмотра в CLI
по умолчанию выбраны demo и регион RU. [Demo API EXBO](https://eapi.stalzone.com/overview.html#demo-api)

`--catalog PATH` задаёт другой JSON с той же структурой. `--json` выводит
один объект с сохранёнными лотами и историей. Категория без значения
отображается как `—` в терминале и `null` в JSON. Код завершения `0`
означает успех, `2` — ошибку выбора или настроек, `1` — недоступность
базы или отсутствие опубликованного снимка.

## Demo

Задайте `STALZONE_DEMO_TOKEN` в окружении процесса. Публичный токен приложения опубликован в документации EXBO. [Demo API](https://eapi.stalzone.com/overview.html#demo-api)

```python
import asyncio
import os

from auction_engine.backend.integrations import AuctionClient


async def main() -> None:
    async with AuctionClient.demo(
        access_token=os.environ["STALZONE_DEMO_TOKEN"],
    ) as client:
        lots = await client.get_lots("EU", "y1q9", additional=True)
        history = await client.get_history("EU", "y1q9", limit=5)
        print(lots.data.total, history.data.total)


if __name__ == "__main__":
    asyncio.run(main())
```

Каждый вызов возвращает одну страницу. В `data` лежат типизированные записи, в `raw` — декодированный JSON со всеми полями EXBO. `received_at` содержит время получения в UTC, `headers` — доступные заголовки времени и квоты. Пустой список в `data.lots` или `data.prices` — допустимый ответ. Поле `price` содержит целое значение из EXBO.

## Production

Для одобренного приложения задайте `STALZONE_CLIENT_ID` и `STALZONE_CLIENT_SECRET` в корневом файле `.env` или в окружении процесса. Настройки на `pydantic-settings` отдают приоритет окружению. [Регистрация приложения EXBO](https://eapi.stalzone.com/registration.html)

```python
from auction_engine.backend.integrations import AuctionClient
from auction_engine.backend.settings import AuctionSettings

settings = AuctionSettings.from_env()
client = AuctionClient.production(
    client_id=settings.client_id,
    client_secret=settings.client_secret.get_secret_value(),
)
```

Используйте клиент через `async with`, как в demo-примере. Токен будет получен при первом запросе.

## Ошибки

Импортируйте исключения клиента из `auction_engine.backend.integrations.auction.errors`.

| Исключение | Ситуация |
| --- | --- |
| `ValueError` | Некорректные аргументы запроса |
| `TransportError` | Таймаут или сбой транспорта |
| `AuthenticationError` | API или сервер OAuth отклонил авторизацию |
| `RateLimitError` | HTTP 429. `retry_after_seconds` содержит задержку в секундах или `None` |
| `ApiHTTPError` | Другой неожиданный HTTP-статус, включая редиректы |
| `ResponseFormatError` | Успешный HTTP-статус с повреждённым JSON или нарушением схемы |

Ошибки API наследуются от `AuctionError`. У `ApiHTTPError` и его подклассов доступны `status_code` и `headers`. Решение о паузе и повторе при `429` или сетевом сбое принимает вызывающий код. При `401` в production клиент обновляет токен и повторяет GET один раз.

## Ручная сверка в RU

1. Сохраните JSON с собственным активным лотом пачки (`amount > 1`).
   После появления продажи повторите запрос. Сопоставьте `buyoutPrice`,
   `amount`, `price`, `time` и фактическую выплату в игре.
2. Добавьте в список артефакт с известными качеством и заточкой. Сравните
   `additional` в лотах и истории. Фиксируйте `{}`, `null` и отсутствие
   поля отдельно.

python -m pip install -r requirements-dev.txt
python -m pytest -q
